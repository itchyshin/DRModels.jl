# predict(newdata) with a factor on the generic routes (gap map v2, area M)

## Finding

For every non-Gaussian family tried, `predict(fit, newdata)` threw unless `newdata` held every level of every factor; a single-row `newdata` threw "only one level found: b (need at least two to compute contrasts)", and a subset threw "the `mu` design built from `newdata` has columns [...] but the fitted coefficients are [...]". Gaussian was fine. Reproduced on the base tip (0bfcde2bb) for a Poisson fit `y ~ x + f`: rows with `f = b` only, rows with `f in {b, c}`: both failed; all three levels: passed.

## Root cause

`_design(...; schema_cache, schema_key)` reuses a stored training schema (factor levels and contrasts) when `schema_cache[]` holds `schema_key`. Only the Gaussian fitters pass the cache at fit time. The other fitters (Poisson, Binomial, Gamma, NB2, Beta, Student, LogNormal, Tweedie, zero-inflated and hurdle routes, cumulative logit, and the random-intercept routes) call `_design(f.response, rhs, data)` with no cache, so the cache stays empty and `predict` builds the schema from the rows of `newdata`: one level gives an error, a subset gives different dummy columns, and a complete but reordered set gives different contrasts only when the first level moves (the column-name guard of #1000 catches that and refuses).

Patching each of the dozens of fitters was rejected: any missed call site brings the bug back. The fix is central.

## Fix

- `@drm_entry` (src/control.jl) calls `_record_factor_levels!(formula, data)` before every fit. It stores, under the reserved key `:__factor_levels__` of the formula's `schema_cache`, the levels StatsModels would give each categorical column of the formula (computed with `StatsModels.concrete_term`, so the order is exactly the fitter's own). Numeric columns are not recorded. It never throws.
- `_design` (src/gaussian_core.jl), on a read-only call (`store_schema = false`, the predict paths) with no schema stored for the parameter but a catalogue present, builds a schema whose factors carry the recorded levels (`_catalogue_schema`; `schema(ft, data, hints)` is not usable because `ContrastsMatrix` insists the data contain every level). It first raises the same missing-column, `missing`-value and unseen-level refusals as the cached-schema path. Gaussian fits, whose schema is cached, take the old path unchanged.
- Fit paths (`store_schema = true`) never read the catalogue, so estimation is untouched.

## R behaviour matched

drmTMB `drm_prepare_model_matrix_newdata` (R/methods.R): rebuilds `newdata` factors with the fitted levels, so a subset or one row works, and aborts with "New prediction data contains unknown factor level(s) for <name>" listing the unknown and fitted levels. Julia now does both; the unknown-level message names the column, the level and the fitted levels.

## Test

`test/test_predict_newdata_factor_levels.jl` (189 expectations, about 75 s single-threaded on Julia 1.10): Poisson, Binomial, Gamma, NB2, Beta, Student, LogNormal; single row (two levels), subset, reordered levels, response and link scale, a `y` column in `newdata`, unseen level (message content), `sigma ~ f` through `predict_parameters`, random-intercept Poisson and Gamma, and a reused `bf` object refit on data with fewer levels. On the base tip: 72 pass, 7 fail, 105 error; after: 189 pass.

## Limits

- The catalogue records levels of the data passed to `drm` before missing-response rows are dropped. A level that occurs only on rows the fitter drops would be catalogued but have no coefficient; `predict` then refuses with the existing column-name message (#1000), never a wrong value.
- A factor typed as numeric codes is a continuous predictor in both packages and is unchanged.
- Fits created by other entry points that do not pass through `@drm_entry` keep the old behaviour.
- The 69 grid cells were not rerun; the seven families of the test, and cumulative logit through the shared `_design`, are the evidence.
