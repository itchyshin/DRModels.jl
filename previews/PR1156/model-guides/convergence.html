Improving convergence ​

Status — Stable

Mirrors drmTMB's Improving convergence. A practical guide to checking and improving a fit in DRModels.jl, built around the check_drm diagnostic.

A distributional regression fits by maximum likelihood: most drm routes run an LBFGS optimiser (with a robust mode-finder for the phylogenetic engine) and store whether it converged. Most models converge without intervention. This page is for the ones that don't — and how to tell the difference between a real problem and a model that is simply sitting at the edge of its parameter space.

Step 1 — check the fit ​

Every fit carries a convergence flag and a covariance matrix for its estimates (on most routes the inverse of the observed information). check_drm bundles the useful diagnostics into one report:

julia
using DRModels
fit = drm(bf(@formula(y ~ x), @formula(sigma ~ x)), Gaussian(); data = dat)
check_drm(fit)

The report is a NamedTuple:

  • converged — did the optimiser report success, and (for Gaussian fits) is the fit non-degenerate, as is_converged decides? This is still a stopping rule, not proof of a maximum (see below).

  • max_abs_grad — max|∇nll| at the solution, the largest slope of the negative log-likelihood. Near a clean interior optimum this is ≈ 0; a large value means the optimiser stopped early.

  • grad_source — how max_abs_grad was obtained. :none or :unavailable means no gradient could be computed, so max_abs_grad is NaN and the gradient was not checked at all.

  • vcov_posdef — is the covariance positive-definite? When this is false, some parameters have no finite standard error (drmTMB's sdreport returns all NaN in exactly this situation).

  • min_eigval / cond — the smallest eigenvalue and the condition number of the covariance. A near-zero min_eigval flags a direction the data barely constrain (a variance pinned near zero, two confounded coefficients).

  • ok — true when converged, the gradient is small, and the covariance is PD. When grad_source is :none or :unavailable, ok = true means only "converged and PD": the gradient test was skipped.

What a true flag does not tell you

converged = true (and is_converged(fit) = true) means the optimiser stopped by its own rules. It does not prove the estimates are at a well-defined maximum. A fit can stop with a parameter at its limit and still report true: a variance estimated at zero, a Student-t nu that runs towards infinity (the data look Gaussian), or a ZeroOneBeta one-inflation part with no exact ones in the data. is_converged adds a check for a collapsed residual SD, but only for Gaussian fits. So read max_abs_grad and grad_source as well, and look at estimates that are very large on the link scale. Work to make the flag stricter is tracked in DRModels.jl#969 and DRModels.jl#949.

Step 2 — read the failure mode ​

A non-ok report is information, not necessarily an error.

A variance at the boundary ​

If a random-effect SD or a scale parameter is estimated near zero, the likelihood flattens in that direction: min_eigval is tiny and the gradient may not reach zero. This is often the correct MLE — the data carry little of that variance component. The Wald standard errors of the other parameters can usually still be used; the boundary direction itself has no meaningful Wald standard error. Prefer confint(fit; method = :profile) there: the profile interval does not rely on the quadratic Wald approximation, which breaks down at a boundary. Its likelihood-ratio calibration is still asymptotic, so it is not exact either.

This applies to variance components estimated at zero. A shape parameter at its limit behaves differently: for Student-t nu running towards infinity, the fit can report a standard error of 0 and a zero-width Wald interval for nu instead of an undefined one (DRModels.jl#969). Do not use that interval; a large nu means the data look Gaussian, and a profile or bootstrap interval, or a Gaussian refit, is the better check.

Confounded predictors ​

A near-singular covariance with a large cond usually means two columns of a design matrix are nearly collinear (e.g. an intercept and a centred covariate that is almost constant). Re-centre or drop one; refit.

An exactly aliased column is a different case: sigma ~ 1 + x + z with z = 2x + 1, or a duplicated column, leaves the likelihood flat along the alias direction, so the coefficient is not identified at all. drm (Gaussian location-scale route) checks the rank of each parameter's fixed-effect design once, warns with fixed_effect_rank_deficiency naming the parameter block and the aliased coefficients, and reports is_converged(fit) == false. The aliased coefficients' standard errors are NaN, and check_drm(fit).ok is false with the blocks listed in check_drm(fit).fixed_effect_rank_deficiency. The log-likelihood and the identified coefficients are unchanged (the covariance is still the pseudo-inverse); drop or recode the aliased column and refit. This matches drmTMB's convergence_status() == "degenerate" for the same designs.

Stopped early ​

If converged is false but max_abs_grad is still sizable, the optimiser ran out of iterations rather than hitting a boundary. A smaller g_tol will not help: it is the gradient size at which the optimiser may stop, so tightening it makes stopping harder, not easier. To raise the iteration cap or supply starting values, pass one DRMControl (the names follow drmTMB's drm_control()):

julia
f = bf(@formula(y ~ x), @formula(sigma ~ x))
fit = drm(f, Gaussian(); data = dat, control = DRMControl(maxit = 2000))

# Start from another fit's estimates, or try five starts and keep the best:
fit2 = drm(f, Gaussian(); data = dat, control = DRMControl(start = coef(fit)))
fit5 = drm(f, Gaussian(); data = dat, control = DRMControl(multi_start = 5))
control_info(fit5).start_logliks     # one log-likelihood per start
control_info(fit5).starts_agree      # false (and a warning) if they disagree

maxit, start and multi_start work on the fixed-effect routes of the univariate families. You can request :lbfgs or :bfgs directly on those primary ML fits. Hold the model, data and internal-scale start fixed when comparing methods:

julia
base = drm(f, Gaussian(); data = dat)
x0 = coef(base)
lb = drm(f, Gaussian(); data = dat,
         control = DRMControl(optimizer = :lbfgs, start = x0))
bf = drm(f, Gaussian(); data = dat,
         control = DRMControl(optimizer = :bfgs, start = x0))
control_info(bf).requested_optimizer   # :bfgs
control_info(bf).actual_optimizer      # :bfgs
control_info(bf).optimizer_runs        # every attempted start and native stopping result

optimizer = :default retains the route's current method and restart policy. Gaussian ML with one mean random intercept (1 | g) also accepts :lbfgs or :bfgs; its data-driven start, conditional restart, exact-gradient check and boundary tie rule still apply. Its own two starts are reported separately in optimizer_runs, and selected_optimizer_stage names the one retained. maxit, start, multi_start, seed and jitter are not available on this random-intercept route. Gaussian selection requires the ordinary ML route with algorithm = :auto, and refuses alternate integration, imputation or profiling options. Other random, structured, bivariate and REML routes refuse an explicit optimizer by name. profile_result, confint(...; method = :profile) and fit-based bootstrap_result, bootstrap_summary and bootstrap_ci refuse fits with an explicit optimizer choice before starting any refit; they cannot yet forward the selected method. Refit with optimizer = :default to use those inference routes. Wald intervals remain available when standard errors were computed. Solver agreement alone does not establish parameter identification.

se = false works on every route:

julia
fit = drm(f, Gaussian(); data = dat, control = DRMControl(se = false))
H = hessian(fit)                    # observed information, `coef(fit)` order
inv(H)                              # the covariance, computed later
g = gradient(fit)                   # ≈ 0 at the optimum
g' * (H \ g)                        # scaled Newton decrement: a stationarity audit

gradient and hessian are of the negative log-likelihood the optimiser minimised, in the same order and on the same scale as coef(fit).

Step 3 — scale and standardise ​

Most convergence trouble is conditioning. Two cheap fixes:

  • Standardise covariates. Predictors on wildly different scales make the Hessian ill-conditioned. Centre and scale continuous covariates before fitting.

  • Use ML for model comparison. ML is the default and is comparable across fixed-effect structures; REML likelihoods are not. Keep ML when selecting models with aic / bic.

Comparing logLik with drmTMB or glmmTMB (#943) ​

For a sigma ~ x + (1 | g) model on NegBinomial2(), Gamma() or Beta(), the default :LA route integrates the random intercept by adaptive Gauss-Hermite quadrature. drmTMB and glmmTMB use the TMB Laplace approximation, so the two log-likelihoods are not comparable: do not compare loglik, aic or an LRT across the engines for these models. The estimates agree closely; the gap is the integration convention, not a different optimum. Measured on lme4 grouseticks, NB2 ticks ~ year + height100 + (1 | brood):

sigma formulaDRModels.jl default :LAdrmTMB / glmmTMB (TMB Laplace)
sigma ~ year-888.350-888.885
sigma ~ 1-889.612-890.203

With sigma ~ 1, marginal = :Laplace reproduces the drmTMB value (-890.2035). That route does not accept a non-constant sigma, and a TMB-convention Laplace for sigma ~ x + (1 | g) is not planned for now, so the comparison is not available for those models.

The phylogenetic engine ​

The verified q=4 phylogenetic location–scale engine has its own mode-finder (sparse augmented-state Laplace with an exact O(p) gradient). Two notes specific to it:

  • Off-diagonal initialisation. Starting the cross-covariance Cholesky away from zero (the lc3/lc7 entries) avoids a saddle near the diagonal start.

  • The Watanabe-singular boundary. When a per-axis phylogenetic variance is near zero the model sits at a singular point; the optimiser flags the plateau rather than chasing a flat ridge. This matches drmTMB's behaviour (it reports "false convergence") — both engines are correct; the geometry, not the optimiser, is the limiting factor.
