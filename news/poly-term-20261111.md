- **`poly(x, d)` now works inside a Julia `@formula`, with R's orthogonal basis.** `@formula(y ~ poly(x1, 2))` used to fail with `UndefVarError: poly` before DRModels ran (eight gap-map v2 cells). `DRModels` now exports `poly`; the columns, the coefficient names (`poly(x1, 2)1`, `poly(x1, 2)2`) and the log-likelihood match drmTMB 0.8.1 for Gaussian, Poisson, Binomial, Gamma, Beta, NegBinomial2, LogNormal and Student (`test/test_poly_term.jl`, reference `test/fixtures/poly_parity/`). Every fit computes the basis from the rows it uses (complete rows, as in R) and stores it in the fit, so `predict(fit, newdata)` rebuilds that fit's training basis at the new rows. A `bf(...)` object holds no basis: fitting twice with the same object on other data gives exactly the result of a fresh object, as R recomputes `poly` on every call. Only `poly(x, d)` with a plain column and a literal integer degree is accepted. `raw = TRUE`, `degree = 2` and `coefs = ...` are not accepted: `@formula` stops them with its own parser error before DRModels runs (write the powers as function terms, or use the R bridge), and several variables or a transformed argument are refused with a DRModels message. Main-term coefficient names (`poly(x1, 2)1`, `poly(x1, 2)2`) match drmTMB; interaction names use DRModels' `&` as for every term (`poly(x1, 2)1 & z`, where R writes `:`). After a plain `import DRModels` (without `using`), write `DRModels.poly` in the formula. This comes from a change that applies to every fit, not only `poly` ones: `drm` now fits on its own copy of the formula and no longer writes factor levels or design schemas into the object you passed, so reusing one `bf(...)` for a second fit with different factor levels is also safe. `fit.formula` is that copy, not your object (`fit.formula === f` is false); code that relied on a fit filling in your formula object must read the fit instead. The R double bar `(1 + x1 || g)` is unchanged: Julia's parser rejects `||` before DRModels sees it, so keep writing `(1 | g) + (0 + x1 | g)`.
